Especificações do Projeto e Diretrizes de Execução para Desenvolvimento de SoftwareResumo ExecutivoA disciplina de Especificação de Software, dirigida pelo Professor Antônio, altera o modelo tradicional de "Trabalho de Conclusão de Curso" (TCC) para os princípios do Manifesto Ágil, priorizando software funcional em vez de documentação extensa. O objetivo central é a síntese dos conhecimentos de desenvolvimento adquiridos anteriormente em um único projeto operacional. Os alunos devem entregar no mínimo quatro funcionalidades completas—uma para cada uma das três avaliações contínuas (ACs) e uma para o exame final. A avaliação é estritamente baseada em "software funcionando", exigindo a integração total de front-end, back-end e banco de dados. As entregas devem incluir um quadro de tarefas, um repositório público no GitHub e uma demonstração concisa em vídeo. O tamanho dos grupos é limitado a no máximo sete alunos.Objetivos e Metodologia do CursoO objetivo principal desta disciplina é a construção de um projeto de software que demonstre a integração de todo o conhecimento de desenvolvimento adquirido ao longo do programa.Transição Ágil: Antigamente um TCC focado em monografia, o curso agora segue o Manifesto Ágil. A principal medida de progresso é o software em operação, e não monografias escritas.Foco Prático: Espera-se que os alunos "coloquem a mão na massa", construindo, integrando e garantindo a funcionalidade de um sistema de software.Flexibilidade de Escopo: Não há um escopo pré-definido. Os projetos podem variar de sistemas de pet shop e farmácias a supermercados ou barbearias; os alunos definem o domínio de negócio.Requisitos do Projeto e FuncionalidadesO projeto deve consistir em, no mínimo, quatro funcionalidades distintas. Uma funcionalidade só é considerada válida se estiver "completa".Projetos de Desenvolvimento de SoftwareUma funcionalidade completa deve abranger três camadas integradas:Front-end: A interface do usuário.Back-end: A lógica do lado do servidor e APIs.Banco de Dados: Armazenamento persistente de dados.Contraexemplos de funcionalidades incompletas:Páginas HTML estáticas ou protótipos de tela elaborados (apenas front-end).Teste de APIs via ferramentas como Postman ou Swagger (apenas back-end/banco de dados)."Sprints de Infraestrutura" (criação apenas de tabelas de banco de dados).Projetos de BI e Análise de DadosPara projetos focados em Business Intelligence ou Análise de Dados, cada entrega deve incluir:Análise Completa: Uma nova análise ou conclusão alcançada através dos dados.Representação Visual: Um novo gráfico ou dashboard para cada etapa de avaliação.Origem dos Dados: Divulgação clara das fontes de dados (ex: Kaggle, dados governamentais públicos ou arquivos CSV). Dados sigilosos ou privados de empresas são estritamente proibidos para evitar problemas legais e de avaliação.Especificações Técnicas e RestriçõesEmbora haja liberdade tecnológica significativa, aplicam-se certas restrições:CategoriaDiretrizesLinguagens de ProgramaçãoSem restrições (Java, Python, PHP, C#, .NET, etc.).Frameworks Front-endSem restrições (React, Angular, Vue.js, React Native, etc.).Banco de DadosDeve usar bancos de dados "reais" (MySQL, SQL Server, Oracle, MongoDB).Bancos ProibidosBancos em memória ou baseados em arquivos como SQLite (exceto para apps móveis) e H2 não são permitidos para aplicações web.Método de DesenvolvimentoPro-code, low-code ou no-code são todos permitidos.HospedagemHospedar a aplicação online não é obrigatório, mas pode render pontos extras. Execução local é aceitável.Entregas Obrigatórias e DocumentaçãoCada avaliação exige três componentes essenciais enviados via plataforma designada (Classroom):Link do Quadro de Tarefas: Um link para um quadro (Trello, Jira ou GitHub Projects) mostrando o backlog, tarefas em andamento e itens concluídos.Link do GitHub: Um link para um repositório público contendo o código-fonte. Projetos privados aos quais o instrutor não tenha acesso não serão avaliados.Demonstração em Vídeo: Um vídeo de 3 a 4 minutos demonstrando a funcionalidade.Requisitos do VídeoAbordagem Didática: O vídeo deve focar na funcionalidade, não em uma explicação de código linha por linha.Estrutura: Mostrar o Quadro de Tarefas, demonstrar o software rodando (login, entrada de dados) e mostrar uma consulta ao banco de dados (Select) para provar a persistência.Concisão: Vídeos que excedam 20-30 minutos são desencorajados, pois dificultam o processo de avaliação.Critérios de Avaliação e NotasSoftware Funcionando: Esta é a métrica mais crítica. Se o professor tiver dúvidas sobre a funcionalidade, ele baixará o código. Se não rodar, a nota é zero.Priorização Ágil: As funcionalidades devem ser entregues com base no valor. Entregar um sistema de "Login" como a primeira funcionalidade é desencorajado; os alunos devem priorizar recursos principais do negócio (ex: cadastro de produtos em um sistema de supermercado).Cronograma de Notas: Dado o volume de alunos, as notas são geralmente publicadas em até 10 dias após o prazo de entrega.Gestão de Grupo: Grupos de 1 a 7 alunos. Todos os membros devem enviar o link/arquivo no Classroom para garantir a nota.Exame Final e Avaliação SubstitutivaExame Final (Prova): Consiste na implementação de uma nova funcionalidade (a quarta) e no fornecimento de Diagramas de Classe e Diagramas de Caso de Uso.Avaliação Substitutiva (Sub): Não há prova teórica. Para passar na Sub, o aluno deve entregar e apresentar uma nova funcionalidade.Datas ImportantesAC1: Meados de março.AC2: Meados de abril.AC3: Maio.Exame Final: Início de junho (Prazo absoluto, sem atrasos permitidos).
